### 1. SOLID Principles
1. S - Single Responsibility Principle (SRP):

    Each class should have one, and only one, reason to change—meaning it should have a single responsibility.</br>

    **What does this mean?**</br>
    It means that a class should be responsible for just one role. Following this principle is crucial to avoid unintended side effects.
    
    For example, suppose a class handles two roles—buyer and seller. These roles often have the conflict rules. If a new developer, unaware of the side effects, modifies the code to make a change for the buyer, it could unintentionally cause a million-pound loss for the seller.
    
    This scenario highlights why the class does not adhere to SRP and demonstrates the importance of separating responsibilities.

2. O - Open/Closed Principle (OCP):

    Software entities should be open for extension but closed for modification.

    > You should be able to extend the behavior of a system without having to modify that system.</br>
    > -- Uncle Bob(the auhtor of Agile Manifesto)

    This principle simply means that we should be able to add new features or behaviours to our system without altering the existing code.

    **Example:**
    Imagine we have a class that calculates discounts. Initially, it supports percentage-based discounts. Later, we need to add a new type of discount—say, a fixed-amount discount.

    **Bad Approach (Violating OCP):**
    We modify the existing class to add a condition for the new discount type. This change could unintentionally break existing functionality.

    **Better Approach (Following OCP):**
    We create a new class for the fixed-amount discount, extending the behaviour of the system without modifying the original class.

    By following OCP, we reduce the risk of introducing bugs and make the code easier to maintain and extend in the future.

3. L - Liskov Substitution Principle (LSP):

    > Objects of a superclass should be replaceable with objects of a 
    > subclass without affecting the correctness of the program.
    > 
    > -- Barbara Liskov's essay
    
    1. Precondition - Children should have more relaxed input constraints (or at least the same)
       Why? If children have more strict constraint, it won't be able the input that parents have.
    2. Postcondition - Children should have stricter output constraints (or at least the same)
       Why? If children have more relax output, it will violate the parents' expectation
    3. Invariants - Children must preserve the restrictions (invariants) of the parent.
       It is a constant and `must` rule in the parent so does children.

    Be cautious when using inheritance. It is a highly dependent feature, and even a small mistake can cause a subclass to behave in unexpected ways. Once the system is fully developed, fixing such issues can turn into a nightmare.

    Rust does not have inheritance like traditional object-oriented languages (e.g., Java or C++). Instead, it uses traits and composition to achieve **polymorphism**. This design inherently encourages adherence to LSP by avoiding some of the pitfalls caused by inheritance in other languages.

4. I - Interface Segregation Principle (ISP):
    
    Clients should not be forced to depend on interfaces they do not use.

    When traits that you do not need are changed, you may be affected by these changes—even without realising it. Essentially, you can be broken by dependencies you do not use.

    This highlights the importance of avoiding unused dependencies.

    In Rust, developers are encouraged to design smaller, more focused traits as part of the API(code level) specification. This approach ensures that clients depend only on what they need, reducing the risk of being impacted by unrelated changes and making the codebase easier to extend and maintain.
    
5. D - Dependency Inversion Principle (DIP):
    
    High-level modules should not depend on low-level modules; both should depend on abstractions.

    High-level code (business logic) should not directly depend on low-level code (implementation details).
    ```rust
    // Bad Example
    struct FileLogger;

    impl FileLogger {
        fn log(&self, message: &str) {
            println!("Log to file: {}", message);
        }
    }

    struct Application {
        logger: FileLogger, // Direct dependency on FileLogger
    }

    impl Application {
        fn run(&self) {
            self.logger.log("Application started."); // Hardcoded dependency
        }
    }

    // Follow DIP
    // Abstraction (Trait) - Both high-level and low-level modules depend on this.
    trait Logger {
        fn log(&self, message: &str);
    }

    // Low-level module 1
    struct FileLogger;

    impl Logger for FileLogger {
        fn log(&self, message: &str) {
            println!("Log to file: {}", message);
        }
    }

    // Low-level module 2
    struct DatabaseLogger;

    impl Logger for DatabaseLogger {
        fn log(&self, message: &str) {
            println!("Log to database: {}", message);
        }
    }

    // High-level module
    struct Application<T: Logger> {
        logger: T, // Depend on abstraction (trait) instead of concrete type
    }

    impl<T: Logger> Application<T> {
        fn run(&self) {
            self.logger.log("Application started.");
        }
    }
    ```

### Onion Design (Repository)
In the Repository Design Pattern, there is an additional layer between the Controller and the Model—the Repository Layer. This design allows the Model layer to focus solely on representing the database schema and handling database-specific logic. The Repository Layer acts as an intermediary, where business logic related to data access and manipulation is implemented, preventing the Model layer from being burdened with business logic or becoming overly complex.

This separation of concerns offers several benefits:
	1.	The Model Layer remains clean, focusing only on database interactions (e.g., schema definitions, queries).
	2.	The Repository Layer can encapsulate and centralize data access logic, making it easier to maintain and reuse.
	3.	When performing database migrations or schema updates, you can modify the Model Layer without affecting the Repository Layer or other parts of the application.

By isolating business logic in the repository layer, the overall codebase becomes more modular, maintainable, and testable.

| Need for Decoupled Layers                         | Tightly Coupled System Requirements                 |
| Testability and Mocking of Data Access            | Minimal Testing Requirements                        |
| Independent Domain Logic                          | Simple CRUD Operations Without Complex Logic        |

### Domain-Driven Design(DDD)
```
.
├── contexts
│   ├── user_context             # Bounded Context: User
│   │   ├── domain               # Core domain layer
│   │   │   ├── models           # Entities, Value Objects, and Aggregates
│   │   │   ├── services         # Domain Services (pure business logic)
│   │   │   └── events.rs        # Domain events
│   │   ├── application          # Application layer
│   │   │   ├── services         # Application Services (use cases)
│   │   │   └── dto              # Data Transfer Objects
│   │   ├── infrastructure       # Infrastructure layer
│   │   │   ├── repositories     # Repository implementations
│   │   │   ├── models           # Database models (if different from domain models)
│   │   │   ├── services         # External services (e.g., email, logging)
│   │   │   └── databases.rs     # Database connection and configuration
│   │   ├── api
│   │   │   ├── controllers      # REST or GraphQL controllers
│   │   │   └── routes.rs        # API routes
│   │   └── main.rs              # Entry point for the context (if microservice)
│   ├── product_context          # Bounded Context: Product
│   │   ├── domain
│   │   │   └── ...
│   │   ├── application
│   │   │   └── ...
│   │   ├── infrastructure
│   │   │   └── ...
│   │   └── ...
│   └── order_context            # Bounded Context: Order
│       ├── domain
│       │   └── ...
│       ├── application
│       │   └── ...
│       ├── infrastructure
│       │   └── ...
│       └── ...
├── shared                       # Shared Kernel (if needed)
│   ├── utils.rs                 # Common utilities (e.g., logging, configuration)
│   ├── events.rs                # Shared domain events
│   ├── constants.rs             # Shared constants
│   └── ...
└── docker-compose.yml           # Compose file for running multiple contexts
```
| **When to Use DDD**                                | **When Not to Use DDD**                              |
|----------------------------------------------------|------------------------------------------------------|
| Complex business logic and domain-specific rules   | Simple CRUD applications with minimal business logic |
| Large teams or long-term projects                  | Prototypes or short-lived projects                   |
| Need for scalability and maintainability           | Low complexity or single developer projects          |
| Multiple teams with distinct business capabilities | Projects with minimal domain complexity              |
| Focus on aligning software with business goals     | When speed of delivery is the top priority           |
